# Contrato G2 — sweeps (busca de hiperparâmetros)

Depende de G1 (runs). Papéis: ler = viewer; criar/parar sweep e `next` = member. Sem ADR novo: segue ADR-008 (runs/métricas).

## Conceito

Um **sweep** define um espaço de busca, um método e uma métrica-alvo. Agentes (processos do usuário, via SDK) pedem a próxima configuração, executam o treino como um **run** do G1 ligado ao sweep, reportam a métrica por passo e recebem a instrução `continue` ou `stop` (poda). O servidor é o único dono do estado do método (determinístico dado a semente), então vários agentes em paralelo recebem configurações distintas.

```ts
type Param =
  | { type: "choice"; values: (string|number|boolean|null)[] }
  | { type: "int"; min: number; max: number; step?: number; log?: boolean }
  | { type: "float"; min: number; max: number; log?: boolean; q?: number }
  | { type: "constant"; value: unknown };
type SweepConfig = {
  method: "grid"|"random"|"tpe";
  metric: { key: string; goal: "minimize"|"maximize" };
  parameters: Record<string, Param>;
  early_stop?: { type: "hyperband"|"asha"; min_iter: number; max_iter?: number; eta?: number /*3*/ };   // passo = step da métrica
  max_runs?: number; seed?: number;
};
type Sweep = { id: string; name: string; status: "running"|"paused"|"finished"|"stopped"; config: SweepConfig;
  created_at: string; created_by: string|null; run_count: number; best_run_id: string|null; best_value: number|null };
```

## API (`/api/v1`)

- `POST /sweeps` `{name, config}` → `201 Sweep`; valida o espaço (grid precisa só de `choice`/`int` com `step`/`constant`, e tamanho ≤ 100 000 combinações; `log` exige min > 0; `max_runs` ≤ 10 000) → `422` com mensagem por parâmetro.
- `GET /sweeps` · `GET /sweeps/{id}` → `{sweep, runs: [{run_id, status, params, last_value, best_value, pruned: boolean, step}] , importance: {param: number}[]|null}` (`importance` só com ≥ 10 runs concluídos).
- `POST /sweeps/{id}/next` `{agent_id?}` → `200 {run: {id}, params: Record<string, unknown>}` — cria o run (com `sweep_id`, `params` fixados) **ou** `204` quando o sweep terminou (grid esgotado, `max_runs` atingido ou parado). Chamadas concorrentes nunca recebem a mesma configuração (grid/random) e o TPE usa só resultados já registrados.
- `POST /sweeps/{id}/runs/{run_id}/report` `{step, value}` → `200 {action: "continue"|"stop"}` — registra a métrica-alvo (também grava no G1 sob a chave da métrica) e consulta a regra de poda. `stop` marca o run como podado (`pruned=true`); o agente deve encerrar com `status="killed"`.
- `PATCH /sweeps/{id}` `{status: "paused"|"running"|"stopped"}` (pausado → `next` devolve `204` com cabeçalho `Retry-After`).
- `DELETE /sweeps/{id}` (admin) → `204`; mantém os runs, sem `sweep_id`.

## Métodos (implementação própria, sem dependência de Optuna)

- **grid**: produto cartesiano em ordem determinística (embaralhada pela semente quando `seed`), cada combinação entregue uma vez.
- **random**: amostragem independente por parâmetro (uniforme, log-uniforme, `q` quantizado, `int` com `step`).
- **tpe** (Tree-structured Parzen Estimator): 10 (configurável) amostras aleatórias iniciais; depois divide os resultados em "bons" (quantil γ = 0,25 da métrica, respeitando `goal`) e "ruins", ajusta densidades por parâmetro (Parzen com kernel gaussiano para numéricos, categórica suavizada para `choice`) e escolhe, entre N candidatos (24) amostrados da densidade dos bons, o que maximiza `l(x)/g(x)`. Parâmetros independentes (TPE univariado, como no Hyperopt original). Resultado reprodutível para a mesma semente e o mesmo histórico.
- **Poda**: Hyperband assíncrono / ASHA. Degraus (rungs) em `min_iter · eta^k` até `max_iter`; ao reportar num degrau, o run só continua se estiver entre os `1/eta` melhores dos que já passaram por aquele degrau (comparação no mesmo passo, respeitando `goal`); enquanto houver menos de `eta` resultados no degrau, continua. Nunca poda antes de `min_iter`. Para Hyperband com várias "brackets" (s_max > 0) o servidor atribui cada run a uma bracket de forma round-robin.

## Importância dos hiperparâmetros

Floresta aleatória (scikit-learn, extra `analytics` do worker) com os parâmetros como features (categóricos one-hot, `log` aplicado) e a métrica final como alvo; importância por impureza média normalizada para somar 1; calculada sob demanda e cacheada por contagem de runs. Sem scikit-learn instalado a API devolve `importance: null`.

## SDK

```python
sweep_id = matrix_sdk.sweep(config={...}, name="lr-search")           # cria
def train():
    run = matrix_sdk.start_run()                 # dentro do agente já vem ligado ao sweep e com params do servidor
    for step in range(100):
        loss = ...; run.log({"loss": loss}, step=step)
        if run.should_stop(): break              # consulta o report de poda
matrix_sdk.agent(sweep_id, function=train, count=20)    # laço next → train → next; nunca aborta por erro de um run (marca failed e segue)
```
`run.config` contém os params entregues. `agent` aceita `agent_id` e roda em paralelo em vários processos.

## Web

`/sweeps` (lista com status, melhor valor, nº de runs) e `/sweeps/[id]`: gráfico de **coordenadas paralelas** (um eixo por parâmetro + eixo da métrica, cor pelo valor, filtro por faixa em cada eixo, runs podados em cinza), **importância** dos parâmetros (barras), tabela de runs ordenável com destaque do melhor, curva da métrica por run (pods marcados), botões pausar/retomar/parar, formulário de criação com validação do espaço e pré-visualização do tamanho do grid.
